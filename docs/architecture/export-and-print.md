# Export & print

Save As, the Export As submenu, HTML/PDF/RTF export, print, typography presets, and destination safety.

Extracted from `CLAUDE.md` so the always-loaded file stays scannable. Content is verbatim —
these are the same load-bearing notes, not a summary. Read this file before changing anything
in this area.

- Rich PDF export + Print (⌘P): **File ▸ Print… (⌘P)** renders the document the way Read mode does — headings, inline styling, lists, blockquotes, tables, inline + block math, mermaid diagrams, fenced code — to a paginated print job, regardless of the current display mode; **PDF / Styled PDF export live in the File ▸ Export As submenu** (see the "Save As vs. Export As" bullet), not in Save As. Both reuse `MarkdownPreviewRenderer` via `DocumentExportRenderer` (`Lineform/Preview/DocumentExportRenderer.swift`): one offscreen TextKit-1 `NSTextView`, hosted in a borderless never-ordered-front `NSWindow` (an `NSPrintOperation` view with no window prints unreliably — the interactive path fails with "Error while printing"), driven by `NSPrintOperation` for both Print (interactive panel) and PDF export (`.save` job to the Save As URL). Print is a `CommandGroup(replacing: .printItem)` posting the window-scoped `printDocument` notification handled in `EditorContainerView` (the Rename/Delete pattern); export-write failure shows the app's native in-window SwiftUI `.alert` (never `NSAlert`). **A sandboxed app cannot spool a print job without `com.apple.security.print`** — it is in BOTH `Lineform.entitlements` and `LineformDebug.entitlements` (a plain boolean sandbox entitlement, satisfiable under ad-hoc signing, so Debug/CI still launch; do not remove it or Print breaks with "This application does not support printing"). The page is **always white with the app's near-black ink** regardless of the reader theme — forced via an export `ReadingProfile` pinned to the static `.system` theme (no renderer theme change), plus an `ExportTextView` that paints the page white (NSTextView's `backgroundColor` is not carried into the print context; the content area is white, the 1" margins render white in normal viewers). Body type is a **small document size** driven by the preset (`ExportTypographyPreset.bodyPointSize`, 10pt for both presets — the old flat 12pt `DocumentExportRenderer.bodyPointSize` now backs only the test-only `exportProfile(from:)`), NOT the on-screen reading size — a PDF is a saved/shared artifact and reads like a normal document. **Tables and wide diagrams shrink to fit** the page: tables via an export-only `render(...fitTablesToWidth:)` that gives columns proportional percentage widths (`MarkdownPreviewRenderer.fitColumnPercentages`) so they wrap instead of overflowing; mermaid images already cap at the content width. Paper sizes: US Letter / US Legal / Tabloid + A4 / A3 / A5 (`ExportPaperSize`). Real image FILES now render in the **Styled PDF/Print** path (Normal PDF keeps the `🖼` placeholder since it prints raw source; RTF keeps caption/source text) — see the inline-local-image bullet; mermaid + math render as images and appear in the PDF. The PDF-byte tests (which invoke `NSPrintOperation`, whose OS cold start is environment-sensitive) live in the **hosted** plan (`DocumentExportPDFHostedTests`); pure metric/profile/fit-math + a print-free view test stay in the default plan. This **replaced** the old plain-text `LineformDocument.pdfData()` / `.pdf` writable type. See `docs/superpowers/specs/2026-07-04-pdf-export-print-design.md`.

- Save As vs. Export As (2026-07-26, supersedes the 2026-07-18 single Format picker, which had itself replaced an earlier Export As submenu): **saving and exporting are separate commands.** **File ▸ Save As… (⌘⇧S)** retargets the document's own `.md` and has NO Format popup — a plain `NSSavePanel` pinned to the markdown content type. **File ▸ Export As ▸** (HTML… / PDF… / Styled PDF… / Rich Text (.rtf)…) writes a COPY and never touches the open document. Both sit in the same `CommandGroup(replacing: .saveItem)` so macOS's native Duplicate no longer steals ⌘⇧S; Export As deliberately has NO shortcut. The reason for the split: under the old picker a "Save" could produce a PDF, which is not your document and cannot be reopened as one. The cost, accepted knowingly: ⌘⇧S no longer reaches PDF, and no compatibility shim was left behind — a transitional duplicate means maintaining two paths forever. Save As posts the window-scoped `saveAsDocument` notification; each Export row posts `exportDocument` carrying its `ExportFormat.rawValue` in the payload's `value`. `EditorContainerView.exportDocument(_:)` presents an `NSSavePanel` whose accessory (`ExportPanelController`, `Lineform/Editor/SaveAsExport.swift`) is only the format's one-line description plus a Paper Size popup for the two PDF formats — there is no Format popup, because the menu row already chose. The accessory HUGS its content (natural label widths, no fixed-width container) so `NSSavePanel` centers it like TextEdit's format popup — do not pin it full-width or it left-aligns. Menu icons come from `MainMenuIconDecorator.symbolsByTitle` keyed on `normalizedTitle` (which strips the trailing `...`): Export As is `square.and.arrow.up`, deliberately the outbound counterpart of Save's `square.and.arrow.down`. Format behavior: **Markdown** (Save As only) drives the backing document's own `save(to:ofType:for:.saveAsOperation)` — a REAL macOS Save As that retargets `NSDocument.fileURL` and routes through the FileDocument `fileWrapper` write (so `recordWrite` → the `savedAt` observer re-points the reload watcher and `currentFileURL`, and an Untitled doc actually becomes the file); a raw `Data.write` would leave the in-app document detached, so never revert to it. **RTF** uses `DocumentExportRenderer.rtfData(for:profile:paper:)` (native `NSAttributedString` RTF writer — pure/fast, default test plan, no `NSPrintOperation`); because `.rtf` can't portably embed images, math/mermaid export as **caption/source text** via the `imagesAsText` flag threaded through `MarkdownPreviewRenderer` (default `false`, so on-screen/PDF is unaffected), and tables serialize best-effort as `NSTextTable`. DOCX was dropped (no native writer; RTF opens cleanly in Word/Pages/Google Docs/TextEdit). **Destination guards (2026-07-19):** (a) Save As — and ONLY Save As, since `.html`/`.pdf`/`.rtf` are not openable document types so no tab can hold one — refuses a destination already open in **another tab, in any window** — `SaveAsConflict.conflictingTabTitle` (pure, in `SaveAsExport.swift`) is fed `EditorTabStore.allOpenTabs` and the handler shows a "File Already Open" alert instead of writing. The panel's own "Replace?" warning is about the file on disk and says nothing about the other tab, whose stale in-memory snapshot would autosave straight back over the new bytes (silent data loss). Refusing — rather than deduping/merging tabs — matches AppKit's own refusal to save one document onto another open document's file, and never closes a tab out from under the user. Load-bearing details, each one a bug that was actually hit: **(i)** the app-wide view comes from a static `NSHashTable.weakObjects()` registry on `EditorTabStore` (stores register in `init`; weak so a closed window drops out with no unregister call, plus a `#if DEBUG resetRegistryForTesting()` since the registry is process-global and the suite shares one process). **(ii)** The active tab's own file is excluded **by PATH, not just by tab ID** — the same file can be open in a second window, and an ID-only check would refuse the most routine Save As there is ("keep the same name") with no override. **(iii)** That exclusion is what makes open-time dedupe load-bearing: `EditorTabStore.locate(_:preferring:)` reveals the window that already has a file instead of opening a second copy, so a second tab on the active tab's own file is not reachable through any IN-APP open (sidebar, ⌘K, cross-file search — all route through `EditorContainerView.openSidebarFile`). ⌘O/Finder/CLI/App Intents are covered by the second half, `DuplicateWindowMerge` + `EditorContainerView.handOffToExistingWindowIfDuplicate`: those build a fresh window through DocumentGroup before any of our code runs, and AppKit's own dedupe misses them because it compares `NSDocument.fileURL` — which this app repoints to the ACTIVE tab's file — so a file in a BACKGROUND tab opens as a genuinely distinct second `NSDocument` (verified by tracing the live app). The duplicate window therefore selects the file's existing tab, fronts that window, and closes its own document. **Two dead ends, do not retry them:** installing an `NSDocumentController` subclass to widen `document(for:)` **crashes at launch** (SwiftUI's `PlatformDocumentController` must be the shared controller — SIGSEGV in `applicationWillFinishLaunching`); and hooking `onAppear` does nothing, because a freshly opened window runs it with BOTH its window number and its file still nil. The live hook is the `currentFileURL` change. Handoff is gated hard (`shouldHandOff`): single-tab, unedited, and only the HIGHER window number yields, so two windows restoring one file at launch can't close each other. **Verifying this by hand requires `open -a <BUILT_PRODUCTS_DIR path>`** — a bare `open file.md` hands the file to whatever Lineform Launch Services prefers (often an installed release build), which silently produces a duplicate window that the Debug build never saw, and reads exactly like the fix failing. `openSidebarFile` routing is the pure, tested `SidebarOpenRoute.route` (selectHere / reveal / retryReveal / openHere): `preferring: tabStore` keeps a file this window already has from teleporting the user elsewhere (`NSHashTable` order is unspecified); a revealed window is **deminiaturized** before `makeKeyAndOrderFront` (otherwise a minimized owner swallows the click); and an unresolvable owning window **retries up to `revealRetryBudget` runloop turns** rather than opening a duplicate, because the store learns its window from a binding SwiftUI publishes a tick late and re-attaches on every detail-hierarchy rebuild. The retry re-`locate`s from scratch so a second click can't double-open. `whenOpenedHere` is a callback, not a Bool return, precisely because the reveal path can defer — cross-file search uses it to clear its results ONLY when the document landed in this window. **(iv)** Sameness is decided by PATH — both sides through `standardizedFileURL.resolvingSymlinksInPath()` (the only thing that follows a symlink at the LAST component), then `canonicalPath`, falling back for a not-yet-created destination to the symlink-resolved-then-canonicalized PARENT plus the file name. Do NOT mix `canonicalPath` with `resolvingSymlinksInPath` per-branch: they normalize `/private` in OPPOSITE directions, so one file in two spellings yields two keys and the guard waves the clobber through. Do NOT lowercase to "fix" case: a wrong refusal has no in-app override. **(v)** Two HARD LINKS to one inode are deliberately NOT a conflict (an early inode-identity version got this wrong): every write here is a safe-save — `.saveOperation`, `.saveAsOperation`, autosave-in-place and `Data.write(.atomic)` were all measured to write a temp file and rename, which breaks the link and leaves the sibling's contents intact. (b) **PDF export is staged, never written in place**: `NSPrintOperation` renders straight into its `jobSavingURL`, so overwriting truncated the old PDF the instant the job started and a failed render left it corrupt. `DocumentExportRenderer.writePDFAtomically` wraps the render in `AtomicFileWrite.write(to:produce:)` (in `DocumentExportRenderer.swift`), which renders into a staging file in the app's **own temporary directory** — deliberately NOT a sibling of the destination, since an `NSSavePanel` grant covers only the chosen path — and only copies the finished, **non-empty** bytes into place with a single atomic write. A failed export therefore leaves the destination exactly as it was (including not existing), which is why the old "delete it if we created it" cleanup is gone. It copies through memory rather than moving because `moveItem` fails on an existing destination; the trade is one PDF held in RAM briefly, and an overwritten file getting a new inode (so its Finder tags don't carry over — same trade the RTF branch already made). The plain `writePDF` still writes in place and is for temp-file callers (`pdfData`) only. Each format has its own native SwiftUI `.alert` on write failure (`markdownSaveErrorFileName` / `pdfExportErrorFileName` / `rtfExportErrorFileName` / `htmlExportErrorFileName` — never cross-wired). The four are presented through one `WriteFailureAlert` `ViewModifier` rather than four inline `.alert`s: four copies in `body` exceeded the type-checker's budget and FAILED THE BUILD, the same failure mode as the toolbar `Visibility.hidden` note in `tabs-and-windows.md`. The old `exportPDF`/`exportRTF` notifications + their handlers + the `ExportStylePreference` persistence were removed with the Export As menu.

- PDF export presets — Normal vs Styled (2026-07-18, supersedes the earlier 4-preset Standard/Manuscript/Compact/Article set): exactly **two** `ExportTypographyPreset`s (`Lineform/Preview/ExportTypographyPreset.swift`, pure/tested), surfaced as the **PDF** and **Styled PDF** entries in the Save As Format picker. **Normal** (`.standard`, `rendersMarkdown: false`, `inheritsUserProfile: false`) prints the **raw markdown SOURCE** — visible `#`, `**`, backticks — in a monospaced document face (`DocumentExportRenderer.rawSourceAttributedString`, `DiagramPalette.ink(isDark:false)`), ignoring the user's reading profile entirely (builds from `ReadingProfile.original`); this is "plain markdown," NOT the rendered view. **Styled** (`.styled`, `rendersMarkdown: true`, `inheritsUserProfile: true`) renders the document the way Read mode does, using the user's **SELECTED** reading profile (their font face + line height carry through) at a small document body size. Both pin the light `.system` page + no high contrast + a small body size — no colored/dark-page PDFs, PDF/Print only, on-screen rendering untouched. `DocumentExportRenderer.makeExportTextView` branches on `preset.rendersMarkdown` (renderer vs raw source); `preset.exportReadingProfile(basedOn:)` starts from `.original` for Normal and the user's profile for Styled. **Print (⌘P)** has no style UI and uses `.styled` (print what you read). There is NO persisted style preference anymore (the old `ExportStylePreference` + `UserDefaults` key were removed). RTF export borrows a preset only for its neutral 10pt profile and always renders (never raw source). See `docs/superpowers/specs/2026-07-18-pdf-export-themes-design.md`.

- HTML export (2026-07-26): `MarkdownHTMLRenderer` (`Lineform/Preview/MarkdownHTMLRenderer.swift`) walks the same `[MarkdownBlock]` grouping the preview renderer uses (`markdownBlocks(in:)`) and emits semantic HTML — headings, `ul`/`ol` with disabled task checkboxes, `blockquote` (callouts as `<blockquote class="callout callout-note">`), `table` with per-column `text-align`, `<pre><code class="language-x">`, `hr`. It is pure `String` in / `String` out (Foundation only, no AppKit), so its tests live in the DEFAULT plan. **The one rule: output is ONE-TO-ONE with the source.** Image paths, link URLs, and remote `http(s)` URLs are emitted **exactly as the user wrote them** — never resolved against a document directory, never rewritten, never inlined as `data:` URIs. Someone exporting HTML is technical and their intent is what they typed; keeping the `.html` beside the `.md` keeps their relative paths working, locally and on a web server. Self-contained output is what PDF is for. An earlier design inlined local images as `data:` URIs (a constraint inherited from a paste-into-email use case that had already been cut) and consequently needed a special case for unsaved documents whose relative paths cannot resolve — **both were removed; do not reintroduce either.** Growing special cases here is the signal that a non-one-to-one default crept back in. **Math and mermaid are the only embedded bytes**, because they have no user-authored path — the picture is generated from the `$$…$$` / ```mermaid source at export time. They arrive through an INJECTED `GeneratedImageProvider` closure (real one in `DocumentExportRenderer.htmlData`, a stub in tests); calling the AppKit renderers directly would drag the whole HTML suite into the hosted plan. A provider that declines falls back to the source in a `<pre>`, so a broken diagram never loses content. Attribute values go through `escapeAttribute`, which additionally encodes newlines as `&#10;` — a mermaid source used as `alt` otherwise splits the attribute across real lines. Code fences carry a language CLASS and **no color spans**: inline colors get overridden by every destination and would bake one theme's ink into a document that outlives it. The shell is `<!doctype html>` + `charset=utf-8` + one embedded `<style>` (neutral light page, system font stack, readable measure) and references **nothing external** — no `<link>`, no `<script>`, no web fonts. There is deliberately no "Styled HTML" second variant: a `<pre>` of escaped `#` markers is strictly worse than the `.md` it came from. There is also no Copy as HTML — Read mode is already `isSelectable`, so ⌘C pastes formatted text into Gmail/Word/Pages today. Design: `docs/superpowers/specs/2026-07-26-html-export-design.md`.

- Shared inline syntax: the six inline-markdown regexes (bold, italic, code, strikethrough, image, link) live once in `MarkdownInlineSyntax` (`Lineform/Preview/MarkdownInlineSyntax.swift`) and are used by BOTH `MarkdownPreviewRenderer` and `MarkdownHTMLRenderer`. They were private to the preview renderer until HTML export needed the same patterns; copying them would mean a construct added to one emitter silently not existing in the other — the exported file quietly disagreeing with what the app shows on screen. Capture group 1 is always the display text, group 2 (where present) the destination.

- **Executable link schemes are dropped from HTML export (2026-07-26).** `MarkdownHTMLRenderer.isExecutableScheme`
  refuses `javascript:`, `vbscript:`, and `data:text/html` in a link destination; the link TEXT still
  renders, so nothing the writer typed leaves the page — it just isn't a clickable piece of code.
  This is NOT an exception to the one-to-one rule and must not be read as licence for more: that rule
  exists so paths are never *resolved or rewritten* for convenience (`images/photo.png` survives
  verbatim, and the tests pin that). A `javascript:` URL is not a path, it is code, and nobody writes
  one in a note they intend to export — so emitting it has no upside and leaves a shared export
  carrying a link that runs script on click. Keep it a CLOSED set of executable schemes, never a
  general URL policy or sanitizer. Browsers ignore ASCII whitespace and C0 controls inside a scheme
  (`java&#9;script:` runs), so the test normalises those away first. **Images are deliberately
  untouched:** `javascript:` in an `img src` does not execute in any current browser, and filtering
  there would risk a legitimate `data:image` payload — which generated math and mermaid images
  depend on. Guarded by `MarkdownRobustnessTests`.
