# Files sidebar

The Files tab: scanning, watching, virtualization, file operations, and the sidebar visual system.

Extracted from `CLAUDE.md` so the always-loaded file stays scannable. Content is verbatim —
these are the same load-bearing notes, not a summary. Read this file before changing anything
in this area.

- Files sidebar file management: the Files tab live-refreshes while visible via a recursive FSEvents watcher per root (`Lineform/Outline/DirectoryEventMonitor.swift`, started/stopped with Files-tab visibility so the iCloud-laziness invariant still holds; both roots also re-scan on tab appearance). Own-process events are deliberately **not** filtered (no `IgnoreSelf`) so autosave/Save As keep the tree and a Date Modified sort current; churn is tamed by FSEvents coalescing plus a publish-only-on-change guard in the store's refresh paths, and — because the recursive `items(in:)` walk runs on the main thread — the monitor-driven rescan is additionally **trailing-debounced** (Task 5, `docs/superpowers/specs/2026-07-05-sidebar-scan-debounce-design.md`): the two FSEvents `onChange` closures route through `scheduleWorkspaceRescan`/`scheduleICloudRescan` (injectable `directoryRescanDebounce`, default `directoryRescanDebounceInterval` 0.75s — which **MUST exceed** `DirectoryEventMonitor.coalescingLatency` 0.5s so continuous autosave-while-typing churn keeps resetting the timer and the walk defers to a single settle-after-pause instead of hitching typing ~every 0.5s), cancelled in `endWatchingForExternalChanges`/`deinit`, with a `> 0` synchronous fast-path (interval 0) so tests stay deterministic. Only the monitor path is debounced; every user-initiated refresh (init, Files-tab appear, sort change, hidden-folders toggle, `setWorkspaceURL`, and the `refreshRoots(affecting:)` rename/delete broadcast) stays instant. Moving the walk off-main is the sanctioned follow-up if a huge-tree pause-settle is ever felt (`items(in:)` is already a pure static fn); it was deliberately NOT done in v1 (highest concurrency risk in this incident-prone area). **UPDATE (Task 5, 2026-07-05): the debounce AND the off-main scan were both correct hygiene but NEITHER was the felt fix on a large workspace — a `sample` profile of the live app showed 71% of main-thread time in SwiftUI view layout (`NSHostingView.layout` → AttributeGraph), not the scan. The real cause: the file tree rendered with recursive NON-lazy `VStack`s and folders default expanded, so a big workspace laid out ~3,840 rows at once and re-laid-them-out on every file switch/republish. Fixed by VIRTUALIZING the tree: `OutlineSidebarView.visibleFileRows(_:collapsedIDs:)` flattens the visible rows depth-first (children only when expanded) into `[OutlineFileTreeFlatRow]`, rendered in a `LazyVStack` so only viewport rows lay out — fast whether collapsed or fully expanded. `OutlineFileTreeNodeView` is now a single flat row (recursion removed; it keeps indentation-by-`depth`, collapse toggle, selection, hover, context menu, accessibility). If you add tree UI here, keep it flat+lazy — do NOT reintroduce recursive `VStack`/`ForEach` for children, or a large workspace freezes again. The scan (off-main + debounced) is retained as hygiene.** Each section (iCloud, workspace) has its own persisted **Sort** row (Name / Date Created / Date Modified — deliberately no Manual; `OutlineFileSortOrder`); a sort change on a live root re-SCANS rather than re-sorts, because the 80-per-folder cap is applied in display order (order decides membership). Right-click on rows: **Open in New Tab** / **Open in New Window** / **Rename...** / **Delete...** / **Show in Finder** for files, **Rename...** / **Show in Finder** for folders (no folder delete, by design). Every item carries an SF Symbol — a menu with some rows iconed and some bare reads as broken. The two open destinations are the opt-in alternatives to a plain click, which switches the current tab in place (see `tabs-and-windows.md`); **⌘-click** is the keyboard equivalent of Open in New Tab (`OutlineSidebarView.opensInNewTab(modifiers:)`, which excludes Control — Control-click IS the context menu and must not also open a tab behind it — and Option, the system drag-copy modifier). The context menu and the VoiceOver rotor share one `rowActionButtons` builder, so the new items are mirrored to assistive tech for free, with native SwiftUI `.alert` dialogs (one `.alert` driven by the `SidebarFileDialog` enum, presented from `EditorContainerView` — deliberately **not** `NSAlert`, which stamps the app icon; only the rare error path uses `NSAlert`). Rename preserves the extension; delete is **trash-only** behind a confirmation whose Cancel is the Return default (the destructive Delete never triggers on Return). File → **Rename...**/**Delete...** menu items act on the current file (disabled for untitled, via `LineformCurrentFileMenuState`). Rename/trash are deliberately **uncoordinated** (`SidebarFileOperations`): main-thread `NSFileCoordinator` writes against the open document's own presenters can deadlock, and presenter-observed trashes make `NSDocument` follow the file into the Trash where autosave resurrects it. Windows retarget instead via `sidebarItemRenamed`/`sidebarFileDeleted` broadcasts (rename re-points the reload watcher with baseline-preserving `DocumentReloadController.noteMoved`, never `register`; a deleted open file becomes untitled-with-content) and sidebars refresh via `refreshSidebarFiles` scoped to the affected root. `@Published` didSet observers **do** fire for assignments in `OutlineFileBrowserStore.init`, so persisted prefs load via direct `Published(initialValue:)` backing-storage init — never plain assignment (that would run the init-forbidden iCloud scan when Show Hidden Folders is persisted on). A deferred change-count re-clear in `LineformSidebarFileOpener.replaceCurrentDocument` prevents SwiftUI's async binding registration from spuriously dirtying freshly swapped documents (the phantom "unsaved changes" prompt).

- Sidebar visual system (nav cleanup, 2026-07-17, `OutlineSidebarView`): every section aligns its icons to ONE **icon column** (`sidebarIconColumnLeading`, 22pt from the sidebar content edge) — tab icons, the bottom Settings row, outline rows, the Files sort icon, root icons, and file/folder icons all share it; disclosure chevrons hang in the reserved slot to its left (`filesChevronSlotWidth`/`filesChevronToIconGap` — a small glyph right-aligned in a wider slot, used by BOTH root headers and tree rows via `OutlineFileRootRow.rootLeadingContent` so the two never drift). **Keep new sidebar UI on this icon column** — don't reintroduce per-section insets or ad-hoc chevron geometry. The three tabs (Outline/Files/Markdown Basics) and the **Settings** row carry **no pill** — state is text color only via `OutlineSidebarView.tabTextColor`: a tab reads darkest when selected (i.e. brightest in dark chrome), a quiet grey otherwise that **darkens** on hover; Settings is the reverse (dark by default, **lightens** on hover). **Every sidebar sub-view (`SidebarTabButton`, `OutlineSidebarRow`/`OutlineSidebarNodeView`, `OutlineFileBrowserView`, `OutlineFileRootRow`, `OutlineFileTreeNodeView`, `OutlineMarkdownBasicsTabView`'s `CopyButton`) takes `usesDarkChrome` THREADED from the theme — it must not read `@Environment(\.colorScheme)` for color.** A nested SwiftUI control re-derives `colorScheme` from the window's `effectiveAppearance`, which drifts to light on the tab/inspector transition (see the multi-document tabs bullet), so an ambient read renders near-black-on-near-black (invisible) selected tab text and file rows on a dark theme. Only the root `OutlineSidebarView` reads ambient `colorScheme`, and only because `EditorContainerView` injects the theme value directly onto it (`.environment(\.colorScheme, …)`); it threads that value down to every child. Symmetric `tabDividerGap` under the tabs, matched by each tab-content's top inset. **Outline rows** get a hover bar; clicking a heading scrolls it to the top of the page **without selecting it on the page** (`MarkdownTextViewRepresentable` collapses the requested selection to a zero-length caret) and bolds it — confirmed by the scroll-settle report, which reads the visible-top character a little BELOW the exact edge (`LineformTextView.visibleTopProbeInset`, must exceed `scrollCharacterRangeToTop`'s 8pt park margin) so the clicked/scrolled-past heading wins over the line sliver above it. Bold is a direct weight swap (a crossfade was tried and reverted — font weight can't interpolate, so it ghosts). **Files rows**: the sort row darkens on hover and its menu is an **inline `Picker`** so the checkmark sits in the OS native selection gutter (matching the Reading-Experience Font menu) rather than a hand-rolled `Label(systemImage:"checkmark")`; root headers are quiet labels (no hover fill) with a leading folder/cloud icon; subfolders read a step lighter (`secondaryTextColor`) and darken toward primary on hover; `.md` file rows keep the hover fill unchanged, and the SELECTED row is the native **unemphasized source-list selection**: `OutlineSidebarView.rowSelectionFillColor(usesDarkChrome:)` (chrome-specific, 2026-07-29). **Light chrome** takes AppKit's `unemphasizedSelectedContentBackgroundColor` lifted 55% toward the page (`rowSelectionFillLightening`) — the raw grey reads heavy against a 0.988 page — which also forced the tree's own fainter hover (`filesRowHoverFillOpacity` 0.045 vs the sidebar's 0.08: the Files tree is the only list with a persistent selection fill, so its hover has to stay clearly under it; the Outline tab keeps the standard strength). **Dark chrome does NOT use the system grey at all** — that swatch is lighter than the nav, so a selected row glowed. It recesses to `darkRowSelectionFillWhiteComponent` = **#282828**, below both the nav and the hover fill, which also lifts the blue label to ~4:1 there against 2.8:1 on the grey. The dark sidebar page itself became **#313131** at the same time — a step BELOW the Quiet page, which renders ≈#3F3F3F rather than #303030 (`Theme.quiet` is `calibratedWhite: 0.19`, a space that is NOT sRGB, so the two numbers are not comparable as written; measure both sides in sRGB or the comparison grades against a colour that never reaches the screen). Under Night (≈#191919) the nav is the lighter surface instead; either way it reads as a distinct edge, which is the point. **Both are specified hexes, so both are built in sRGB, not `calibratedWhite`** — the calibrated grey space is a plain gamma-2.2 ramp and renders a visibly different swatch for the same number (`testDarkChromeSwatchesAreTheSpecifiedHexes`, and `OutlineMarkdownBasicsContrastTests` measures the sRGB swatch for the same reason). **Dark chrome also draws its background OPAQUE** (`backgroundOpacity` 0.94 applies to light chrome only): what shows through the veil is the window behind, which differs per theme (Quiet and Night differ), so a translucent nav renders two different greys and neither is the specified hex. Guarded by `testLightChromeSelectionFillIsLiftedButStillOutweighsHover`, `testDarkChromeSelectionRecessesBelowBothTheNavAndItsHover`, and `testDarkSidebarChromeSitsBelowTheQuietPage`) under a **semibold system-blue** label and icon (`rowSelectionLabelColor(usesDarkChrome:)`) — Finder's source-list pairing, with the weight step the sidebar's tab buttons already use so selection is legible without relying on the blue, specified 2026-07-29 over both the accent-tint-under-accent-label original (2.43:1 dark / 3.24:1 light) and the grey-under-primary-label step between them. Blue-on-grey measures ~3.4:1 light and ~4:1 dark: **below AA, deliberately**, and acceptable only because the grey fill carries the selection state on its own, so nothing depends on reading the blue. `testSelectedFileRowContrastIsBelowAAByDesignAndFillCarriesSelection` records the number so it can't be rediscovered as a bug; the AA rule still binds document ink (`Theme.readableInk`). The label is `systemBlue`, **not** `controlAccentColor` — this is specified as blue and must not follow a pink or graphite accent setting. Both `unemphasizedSelectedContentBackgroundColor` and `systemBlue` are **dynamic** `NSColor`s, so they MUST be resolved inside `performAsCurrentDrawingAppearance` against the sidebar's own `usesDarkChrome` appearance — read ambiently it follows the SYSTEM light/dark and repaints the sidebar's selection in the wrong mode, the same failure the `usesDarkChrome` threading rule above exists to prevent. It is memoized per appearance because `rowBackgroundStyle` is re-evaluated on every body pass of every visible row. `rowSelectionFillOpacity` survives only for the ⌘K quick-open palette, which is a transient accent-tinted list rather than a source list. The workspace action button is the near-black CTA only for first-run **"Choose"** (`isChooseAction`); once a workspace is assigned, **"Change"** is a quiet light grey. **Markdown Basics** section headers match the Files sort label (size 12, medium, inactive-tab grey) and left-align to the boxes, with generous section/header spacing (`OutlineMarkdownBasicsTabView`).

- Show hidden folders: a per-app **View menu** item, **Show Hidden Folders** (⌘⇧., default off, persisted) that reveals dot-directories (`.claude/`, `.agents/`, `.github/`, …) and their Markdown/text files, de-emphasized. `node_modules` and `.git` stay excluded regardless (`excludedDirectoryNames` in `OutlineFileBrowserStore`). Toggling re-scans; hidden files open/watch/render like any other. The menu checkmark is driven by the shared `HiddenFoldersMenuState` (backed by the same `showsHiddenFoldersDefaultsKey`); toggling broadcasts `LineformAppNotification.toggleHiddenFolders` app-wide. A window applies it to its per-window store **only while its Files tab is visible** (the observer lives on the Files-tab view, not the always-present sidebar), and otherwise reconciles on the tab's next `.onAppear`. This deliberately preserves the iCloud-laziness invariant above: the store's expensive scan still only runs when the Files tab is shown, never for windows on the Outline tab or with the sidebar collapsed. (There is no in-sidebar toggle; the older eyeball button was removed.)

- Info sidebar tab: a third Files-sidebar tab (**Outline / Files / Info**, `OutlineSidebarTab.info`) that renders the Markdown syntax reference beside the writing surface, so syntax help is available while typing in **any** mode. It **replaced** the former blocking in-window **Info modal** and its `info.circle` toolbar button (see `docs/superpowers/specs/2026-07-05-info-sidebar-tab-design.md`). Copy is a pure data model (`MarkdownReference` in `Lineform/Outline`, kept concise by `MarkdownReferenceTests`) rendered by `OutlineInfoTabView`: rows are **stacked** (monospaced syntax over a plain-English explanation, not two columns — the sidebar is narrow), section-ruled, and theme-aware. Syntax reuses the sidebar's primary text color; the explanation uses an **AA-safe muted tone** — the sidebar's own light secondary dips to ~3.8:1 against the light page (fine for short Files labels, too low for longer-form reading), so `OutlineInfoTabView.explanationLightWhiteComponent` bumps **only** the light tone darker (0.36 → ~4.9:1) while **reusing** the sidebar's dark secondary (already AA); guarded by `OutlineInfoContrastTests`. The tab is **static content** — no directory scan, no FSEvents watcher — so it preserves the iCloud-laziness invariant (only the Files tab scans). Removing the modal renamed its shared dimming scrim `MarkdownBasicsOverlay` → `MuseModalScrim` (Settings still uses it); the toolbar is left with only the Reading Experience toggle (`EditorToolbarAction`).


## iCloud storage

Moved out of `CLAUDE.md`; the two rules that must never be broken (no iCloud entitlement in Debug,
and the scan stays lazy) remain there under Load-Bearing Invariants.

- Only the Release/production build carries an iCloud entitlement (`iCloud.com.lineform.app`, in `Lineform/Lineform.entitlements`). Debug builds intentionally ship **no** iCloud entitlement (`LineformDebug.entitlements` has none), so `iCloudContainerIdentifier` resolves to nil there and the iCloud root is treated as unavailable. When the iCloud container can't resolve (no entitlement in Debug, or a Release user not signed into iCloud), the Files sidebar **hides the iCloud root entirely** (`OutlineSidebarView.rootIsVisible`) rather than showing a dead entry — so **Debug never shows an iCloud root at all**, and only the Workspace root appears. (Connected-but-empty iCloud is instead shown dimmed with no chevron via `iCloudRootIsDimmed`.) This is deliberate isolation: dev/CI build churn can never touch (and let macOS purge) the real users' production container, and — critically — a restricted iCloud entitlement cannot be satisfied under ad-hoc ("Sign to Run Locally") signing, so giving Debug one would stop the test host from launching on CI. Do not add an iCloud entitlement to Debug. (A separate registered `*.debug` container was tried and rejected for exactly this CI-launch reason.)
- The live iCloud scan (resolving the ubiquity container + enumerating the directory) is expensive and must not run on the main thread at view construction — it would block launch and perturb hosted-view layout. It is deferred to `OutlineFileBrowserStore.refreshICloud()`, invoked when the Files tab actually appears. Init only loads the cached snapshot. Preserve this laziness.
- The store keeps the user's iCloud working set materialized via `ensureDownloaded(...)` (`FileManager.startDownloadingUbiquitousItem`), so evicted (dataless) files don't appear in search yet fail to open or drag. This is realized through the `UbiquitousItemDownloader` protocol so it is testable without real iCloud files.
- App-owned containers are still subject to iCloud purge when macOS believes the app was uninstalled. The durable additional protections are operational, not code: ship updates via Sparkle's atomic in-place swap (never instruct users to delete the old app and drag a new one), and do not run-then-delete locally built Release/Export copies of `com.lineform.app` while signed into the production iCloud account.

## Toggle, watcher, and sort (audited 2026-07-27)

**Hidden-folders OFF deleted real files from the tree.** The OFF branch filtered the last
hidden-INCLUSIVE scan in memory, on the stated claim that it is a superset of the visible tree. It is
not: `items(in:)` applies the 80-per-folder cap BEFORE any hidden filtering, so hidden entries spend
cap slots that a real hidden-off scan would have given to ordinary files — those files then vanished,
and the wrong tree persisted until something else forced a rescan. This is the same reasoning that
already made `applySortOrderChange` re-scan rather than re-sort ("the cap is applied in display
order, so order decides membership"); the hidden path simply never got it. It now re-scans a live
root. In-memory `filteredForDisplay` is kept only for the cached/disconnected fallbacks in
`refreshWorkspaceRoot`, where no scan is possible.

**A moved workspace folder killed live refresh for the session.** `workspaceURL` is assigned in two
places and only `setWorkspaceURL` retargeted `workspaceMonitor`. When the user renames or moves the
workspace in Finder, the security-scoped bookmark follows it and `refreshWorkspaceRoot` silently
re-points `workspaceURL` at the new path — but `DirectoryEventMonitor` binds FSEvents to a path
string and sets no `kFSEventStreamCreateFlagWatchRoot`, so the stream was still on the dead path and
never fired again. The tree visibly recovered and showed the new folder name, which is what made it
invisible. Both writes now go through `retargetWorkspaceWatcher()`. Only hiding and re-showing the
Files tab used to heal it.

**The sidebar could not say WHICH folder it was scanning, and read as a broken scan (2026-07-29).**
`NSOpenPanel.url` is the **selected row**, not the directory being browsed. Clicking a subfolder's
disclosure triangle in list view selects it, so expanding a folder and pressing Choose targets that
subfolder while the panel still shows the parent's contents. The workspace root row then prints only
`lastPathComponent` (`workspaceTitle(for:)`), so a folder nested inside its own namesake —
`Test Folder/Test Folder` — is indistinguishable from the one the user believes they picked, and the
tree correctly reported "No Markdown files" for a genuinely empty folder. Every layer was behaving;
the UI simply could not express which folder it meant. The root row now carries the full path as a
`.help()` tooltip, and the empty state names the scanned path under the message
(`OutlineSidebarView.abbreviatedWorkspacePath`, `~`-relative and clipped from the LEFT so the tail —
the only distinguishing part — survives, with the un-elided path as the `accessibilityLabel` since
the visible string starts in `…`). The home prefix is matched on a COMPONENT boundary: a bare
`hasPrefix` renders `/Users/carlostarrats/x` under a home of `/Users/carlos` as `~tarrats/x`, a path
that never existed, in the one line whose entire job is to name the real folder. `workspaceURL` is
`private(set)` so the view can read it while every write still goes through the store (each one must
also `retargetWorkspaceWatcher()`, per the note above). **Diagnosing this took far longer than it
should have because nothing in the app or its logs named the scanned path** — if you add a root
state here, make it name its folder.

**The global Sort row described an order the files were not in.** 1.3.0 replaced 1.2.0's two
per-section sort rows with one global row whose getter reads `iCloudSortOrder`, while the workspace
tree is still scanned with the independently persisted `workspaceSortOrder`. A profile carried over
from 1.2.0 with different values per section showed a label that lied — and because the 80-cap is
applied in display order, it mis-described which files are on screen, not just their arrangement. The
two keys are now reconciled once at load, preferring the workspace value (the only one a user with no
iCloud root visible could have set). Assigned through `Published(initialValue:)` backing storage, per
the init rule above.
