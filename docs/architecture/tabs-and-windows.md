# Tabs & window chrome

Multi-document tabs, the window/nav chrome rules they interact with, and background-tab data safety.

Extracted from `CLAUDE.md` so the always-loaded file stays scannable. Content is verbatim —
these are the same load-bearing notes, not a summary. Read this file before changing anything
in this area.

- **Multi-document tabs**: each window supports multiple open documents in a tab bar (appears automatically when 2+ tabs are open). Tabs are rectangular, flat, theme-aware, with close buttons and dirty indicators. Each tab maintains independent display mode (Write/Read/Preview). Keyboard shortcuts: **⌘T** (new tab), **⌘W** (close the current tab, or its window when it is the last tab), **⌘]** (next tab), **⌘[** (previous tab). Closing a dirty tab prompts to save (Save / Don't Save / Cancel). Native macOS window tabbing is disabled (`NSWindow.allowsAutomaticWindowTabbing = false`) to avoid duplicate tab bars. Tab state is managed by `EditorTabStore` (in `Lineform/Editor/EditorTabStore.swift`), with the UI in `TabBarView` (`Lineform/Editor/TabBarView.swift`). **Sidebar file clicks SWITCH the current tab in place (2026-07-29)** — `EditorContainerView.replaceActiveTab` swaps the selected tab's document and file via `EditorTabStore.replaceTab` and then runs the ordinary `activateSelectedTab` path, so the incoming file gets the same treatment a tab switch gives it (NSDocument repointed BEFORE the text changes, transient state reset, reload watcher retargeted, title updated). Browsing a workspace previously left one tab behind per file touched. If the outgoing tab holds unsaved work the switch is parked behind a Save / Cancel / Don't Save alert (`SidebarSwitchDialog`); **Save** routes through `SaveThenContinueCoordinator` so the swap happens only in the save's success callback — a cancelled save panel on an untitled tab leaves the user exactly where they were. The dialog carries the caller's `whenOpenedHere` continuation, because the file still lands here after the answer (a cross-file search result clears its results list through it). **`whenOpenedHere` runs ONLY when the file actually loaded** — `replaceActiveTab` returns a `Bool` and every call site gates the continuation on it. A file deleted/moved between scan and click fails to load, the current tab is left untouched, and running `whenOpenedHere` anyway would wipe the search results page while opening nothing (a blank screen). **The `.retryReveal` recursion FORWARDS the original `intent`** — without it the retry re-enters as the `.replaceCurrent` default, so a ⌘-click whose reveal hadn't resolved yet would replace the current tab (and prompt over its unsaved work) instead of opening the new tab the gesture asked for. The additive destinations are opt-in: **⌘-click** or the row's context menu (Open in New Tab / Open in New Window). `SidebarOpenIntent` selects between them; `.newWindow` deliberately skips the app-wide dedupe (asking for a new window is explicit), while the other two keep it — a file already open elsewhere is still revealed rather than opened twice. **⌘K quick open and cross-file search results route through the same function and therefore also switch in place**, which is intended: all three are the same "go to this file" gesture. Closing a window with non-active dirty tabs is blocked by a confirmation sheet so tabs are not silently discarded (`WindowCloseController` in `Lineform/Editor/WindowCloseController.swift`). Closing a **background** (non-selected) tab must NOT re-run `activateSelectedTab` (`EditorContainerView.performCloseTab` guards on `wasSelected`): the selection is unchanged, so re-activating would needlessly clear the still-active tab's live search/Find&Replace + caret and wipe its undo stack. **Tab bar placement (load-bearing, 2026-07-18):** the tab bar lives INSIDE `editorShell`, in the VStack the reading inspector attaches to — so the Reading drawer presents as a full-height trailing column rising under the toolbar/search (exactly like the no-tab case) and the tab strip ends at the drawer's edge. When the tab bar sat ABOVE the inspector's anchor, the drawer was pushed below the strip and drew a floating rounded-corner outline while the toolbar's inspector section tinted a hard-edged patch behind the search aligned with nothing. Do not move the tab bar back above `editorShell`. **Window chrome across the tab/inspector transition (four rules, all pixel-verified 2026-07-18):** (1) toggling the tab bar or inspector rebuilds the detail hierarchy and AppKit can reset the window's explicit appearance to light `.aqua`; `WindowChromeReader.ChromeView` re-asserts the themed appearance on **every** `viewDidChangeEffectiveAppearance` (idempotent via the drift guard). **The sidebar column collapse/expand (`isShowingOutline`/`columnVisibility`) is a THIRD rebuild source with the same reset.** Symptom: the native sidebar-toggle glyph — the one appearance-derived control in the nav band — paints black on the dark toolbar and STICKS, while every explicitly-colored SwiftUI control stays correct (the band itself still looks themed because it is painted by `window.backgroundColor`, which the reset does not touch — that asymmetry is what makes only the glyph go wrong). **Root cause, diagnosed 2026-07-25 round 2: `viewDidChangeEffectiveAppearance` can NEVER fire for this drift.** `EditorWindowChrome.apply` pins `window.contentView.appearance`, and `ChromeView` is a descendant of the content view, so it inherits that PINNED appearance; resetting `window.appearance` alone leaves ChromeView's `effectiveAppearance` unchanged and the self-heal is structurally unreachable. The titlebar does not inherit the content-view pin — it follows `window.appearance` — hence the black glyph. The first fix (a next-tick + ~0.35s re-assert pair chasing the slide animation) only narrowed the window and still lost to a reset landing after the last timer. **`ChromeView` now observes `window.appearance` directly (KVO)** and re-applies on drift — deterministic, timing-free, and independent of where the reset comes from. It cannot loop: the drift guard makes its own write a no-op on re-entry. Do NOT reintroduce timer-based re-asserts for the appearance; `ReassertWindowChromeOnHierarchyRebuild` now covers only the parts of `apply` that nothing observes (the window `backgroundColor`). Guarded by `testWindowChromeReaderHealsWindowAppearanceDriftWithoutAnEffectiveAppearanceChange`, which resets `window.appearance` and asserts the heal WITHOUT invoking any callback by hand (the older drift test invoked `viewDidChangeEffectiveAppearance` manually, which is exactly why it stayed green through the bug). (2) `WindowChromeReader.dismantleNSView` must NOT clear the window appearance — SwiftUI dismantles/recreates the view during those same rebuilds with no guaranteed ordering vs. the replacement's apply, and the clear is what flashed the nav or left it stuck light (black sidebar-toggle glyph on Quiet). (3) The nav band with tabs is themed by the WINDOW's `backgroundColor`, set to the theme page color in `EditorWindowChrome.apply`: without tabs AppKit extends the detail's root scroll view under the titlebar (the toolbar samples the page), but the tab strip as topmost view stops that extension and NO SwiftUI background — plain or `.ignoresSafeArea(.top)` — reaches the titlebar region from inside the inspector container (both tried; Paper's cream nav went neutral). (4) `TabBarView`'s bar fill uses `ignoresSafeAreaEdges: []` so the strip's grey never bleeds into the toolbar's backdrop region. (5) The toolbar MATERIAL is hidden (`.toolbarBackground(Visibility.hidden, for: .windowToolbar)` — spelled with explicit `Visibility`, the bare `.hidden` is ambiguous against ShapeStyle and times out type-checking) so the band shows the page-colored window backdrop directly: with the material, the band could never equal the page color on dark themes (it rendered visibly darker) and it washed Paper's cream toward neutral. Net effect, pixel-verified: the nav band is byte-identical with and without tabs in BOTH light and dark themes, and reads as the same surface as the page. **Known cosmetic limitation (investigated 2026-07-25, decision: ship as-is, do NOT re-investigate blindly):** on a theme switch (e.g. Quiet ↔ Original), the native toolbar chrome — the Aa (Reading Experience) button's native shell and the `.searchable` NSSearchField bezel — visibly CROSS-FADES to the new theme over a fraction of a second, while every custom SwiftUI control (mode segmented control, inspector, sidebar) flips instantly in the same transaction. The fade is intrinsic to the native bezel/material drawing; three independent attempts all produced zero change: (1) applying `window.appearance` inside a zero-duration `NSAnimationContext` with `allowsImplicitAnimation = false`, (2) pinning `appearance` directly on every `window.toolbar.items[].view` in the same pass as the window apply, (3) recursively stripping implicit layer transitions (`contents`/`backgroundColor`/`opacity` → `NSNull()`) on all toolbar item views. Conclusion: the cross-fade is composited inside the native shell (likely WindowServer material re-sample), outside app reach. **Fix options, if it ever becomes worth it:** (a) replace the control's shell with a custom capsule keyed on `usesDarkChrome`, the `EditorModeSegmentedControl` pattern — a working `EditorToolbarPillButtonStyle` for the Aa button was built and verified instant on 2026-07-25, then reverted by product decision (the custom look wasn't preferred over the fade; it was never committed — recipe: a `ButtonStyle` drawing a `Capsule` fill at white 0.10/black 0.06 rest, 0.16/0.10 hover, 0.22/0.14 pressed, 0.5pt hairline stroke, `padding(.horizontal, 9).padding(.vertical, 5)`, wired via `.buttonStyle(...)` in `EditorContainerView.toolbarControl(for:)`); (b) for the search field, replacing `.searchable` with a fully custom SwiftUI `TextField` capsule is the only guaranteed fix (wrapping the native `NSSearchField` would NOT fix it — the fade is in the bezel itself), and it means rebuilding the scope bar (This File/All Files), ⌘F/`searchFocused` binding, Esc/cancel behavior, and narrow-window overflow — a deliberately NOT-taken trade given the search UX's regression surface (see `docs/architecture/search.md`). **Known limitation (intentional):** tabs share the window's single undo manager, so switching tabs clears undo history (`activateSelectedTab` calls `undoManager.removeAllActions()`); per-tab undo stacks are deliberately out of scope (see `docs/superpowers/specs/2026-07-18-review-followups-design.md`). **Tab close is pointer-hover-only by design (no × at rest); VoiceOver/Switch Control users reach it via a per-tab "Close tab" accessibility action** (`TabBarView`, gated on `tabCount > 1`).

- **File > Open is tab-native (2026-09-04):** the standard AppKit Open menu item keeps its native title, ⌘O shortcut, validation, placement, and icon, but `MainMenuIconDecorator` retargets its `openDocument:` action to `LineformOpenDocumentCommandTarget`. SwiftUI can reset existing menu items in place as they open, so the retarget runs on the same add/change/tracking passes as icon restoration. The target asks `NSDocumentController.beginOpenPanel` for the native type-filtered panel and routes the returned sandbox-authorized URLs through `openSidebarFile`, avoiding `DocumentGroup.openDocument` entirely: no intermediate document window exists to flash or close. A selected tab is replaced only when it is untitled, empty, and has no unsaved work. Otherwise the file opens as a new tab in the current window; this includes an edited Untitled tab and every real file. Multiple selected files place the first into a disposable blank when available and add the rest as tabs. Finder/CLI/App Intent opens still arrive through `DocumentGroup` and retain the after-the-fact duplicate-window handoff. Do not replace the shared document controller — SwiftUI's `PlatformDocumentController` owns the document plumbing and a custom controller crashes at launch.

- **Fresh document windows do not expose macOS 26's compositor spring (2026-09-05):** a WindowServer frame trace of Dock reopen proved there was only one `Untitled` window — not a hidden Open browser — but its visible surface grew from roughly 1336×826 through 1362×842 before settling at 1360×840. The content stayed visually stable while the page background, rounded edge, and shadow changed, which made the launch look like two windows flickering. `NSWindow.animationBehavior = .none`, set from `applicationWillUpdate`, immediately after `newDocument`, in `ChromeView.viewWillMove(toWindow:)`, and even followed by an early `makeKeyAndOrderFront`, did not alter one sampled frame: this is a SwiftUI/macOS 26 compositor transition, not AppKit's inferred order-front animation. On macOS 26 only, `ChromeView.viewWillMove(toWindow:)` now gives a newly attached, not-yet-visible window `alphaValue = 0`, then restores it after the measured 0.5-second settle interval. A 0.36-second reveal was frame-stable in the trace but still exposed a tiny edge pulse to a real observer, so keep the visual-acceptance margin. The window remains ordered and participates normally in activation; only the unstable surface is invisible, and the first user-visible frame is the final size at full alpha. Do not merge this with the timer prohibition for appearance drift above: that rule requires KVO because appearance can drift at any time, while this one-shot delay masks a finite OS-owned creation transition and never reapplies theme state. Earlier macOS versions keep their immediate native presentation.

- **The final tab stays in `EditorTabStore` until SwiftUI dismisses its `DocumentGroup` scene (2026-09-04).** Removing it first publishes an empty store synchronously, tearing down the scene state its delegate still needs; after **Don't Save**, that left a visible window with no selected tab, so later ⌘W did nothing. Closing the retained `NSWindow` or `NSDocument` directly instead makes SwiftUI keep the scene alive by installing a replacement blank Untitled file. A dirty tab's `TabCloseDialog` retains its exact owning window through the sheet lifecycle, because dismissing the alert can rebuild the view and clear both its cached controller and `windowNumber`. For the last tab, `performCloseTab` does not mutate the store: `WindowCloseController.prepareForTabApprovedClose` clears the backing document's native dirty bit and restores SwiftUI's original delegate, then the view's environment `dismiss` action closes the document scene. Multi-tab close still removes only the chosen tab and activates its sibling when appropriate.

- **The sidebar toggle is OWNED, not inherited — and the appearance story above does not explain it
  (2026-07-29).** `NavigationSplitView`'s automatic toggle resolves its ink when its window is
  created and NEVER re-resolves. A window created under a dark theme keeps a WHITE glyph for the
  life of that window, so switching to a light theme leaves white-on-white; created light, it
  freezes black and dark themes show black-on-dark. Both reports of "the nav glyph is the wrong
  colour" are this one bug, and the direction only depends on which theme the window was born in.
  **This is NOT the `window.appearance` drift described above**, and two earlier fixes aimed there
  could never land: caught in the act under lldb with the glyph visibly wrong, the window, titlebar
  container, toolbar view, item viewer and SwiftUI's own `ToolbarItemHostingView` ALL reported the
  correct appearance with nothing pinned, and an at-rest appearance probe logged zero mismatches.
  A window created AFTER the switch renders correctly while the existing one stays frozen. The KVO
  self-heal is still right for the drift it was written for — leave it — it just never governed this.
  Tested against a reproduction and each left the glyph frozen: an explicit `colorScheme` on the
  toolbar, pinning AND un-pinning `window.appearance`, dropping the window `backgroundColor` write,
  dropping `.toolbarBackground(.hidden)`, and removing + re-inserting the `NSToolbarItem` (that one
  applies, then SwiftUI rebuilds the toolbar and drops it within the same runloop — do not retry
  AppKit toolbar patching). Owning the item is the only fix: `SidebarToggleReplacement` +
  `EditorSidebarToggleButton` thread the ink from `usesDarkChrome` like every other control here.
  **Three properties of the native item are load-bearing and were each regressed and restored one at
  a time — change any of them and the design changes:** (1) the flexible space before it is what
  pushes the glyph to the sidebar's TRAILING edge (AppKit's layout is
  `[flexibleSpace, toggle, trackingSeparator]`); without it the glyph jumps to the traffic lights;
  (2) the tracking separator is what keeps it pinned there as the sidebar resizes/collapses;
  (3) the button must send AppKit's `toggleSidebar:` down the responder chain — writing the
  visibility binding directly changes the column with NO animation, so the sidebar snapped instead
  of sliding. Scoped to `#available(macOS 26)`, where the freeze occurs and where `ToolbarSpacer`
  exists; earlier systems keep the stock item untouched. **Repro (it does not reproduce warm):**
  persisted dark theme → *fresh build* → launch → new window → switch to a light theme. Ink is
  guarded by `testSidebarToggleInkDiffersBetweenChromes` and
  `testSidebarToggleInkMatchesSegmentedControlFill`; position, tracking and motion are visual and
  are not unit-testable, which is why they are written down here.

- **App-wide sidebar broadcasts must update the TAB STORE before the window guard (2026-07-26).**
  `sidebarItemRenamed` and `sidebarFileDeleted` are deliberately not window-scoped — every window
  decides whether it is affected. But both handlers ran `tabStore.retargetFileURL` /
  `tabStore.markFileDeleted` *inside* a guard that first required the window's ACTIVE file to match,
  so a file open only in a BACKGROUND tab was never retargeted or cleared. Activating that tab later
  pointed the window's `NSDocument` at a renamed-away path, or at a file in the Trash — where the
  next autosave writes it back out, which is the resurrection `SidebarFileOperations` is
  uncoordinated specifically to avoid. The tab-level call is now unconditional and the window-level
  document work keeps its guard. Covered by `testRenameRetargetsABackgroundTabWhileADifferentTabIsActive`
  and `testDeleteClearsABackgroundTabWhileADifferentTabIsActive`; the handler ORDERING itself lives in
  a SwiftUI body and is not directly unit-testable, so the comment there carries the reason.

## Save-All and the dirty indicator (audited 2026-07-27)

**The dot and the prompt disagreed.** `TabBarView` computed its dirty dot from
`DocumentSaveStatus.isDirty` while every other consumer — the close-tab prompt, the close-window
sheet, the `NSDocument.isEdited` sync — used `DocumentTab.hasUnsavedWork`, which additionally treats
`fileURL == nil && !text.isEmpty` as unsaved. Two tabs therefore held content with no indicator: an
untitled tab with typed text (⌘T then type), and a tab whose file was trashed from the Files sidebar
— `markFileDeleted` nils the tab's `fileURL` while the save baseline still says clean, so the tab's
text was the only copy of the file's content anywhere and the tab bar said nothing. Worse, when that
tab is selected the status line still reads "Last save: <time>", affirmatively implying the content
is on disk while the file is in the Trash. The dot now reads `hasUnsavedWork`.

**Save All orphaned an untitled tab from the file it had just saved.**
`SaveTabsBeforeCloseCoordinator` originally drove the whole queue synchronously from its `didSave` callback,
and `activateTab` assigns `backingDocument.fileURL = tab.fileURL` — so activating the NEXT tab
clobbered the URL AppKit had just minted for the untitled one before the view's async
`currentFileURL` write-back could run. The store kept `fileURL == nil`, so `windowShouldClose`
re-ran, showed the same "1 tab with unsaved changes" alert with zero dirty dots, and a second Save
All opened another `NSSavePanel` that wrote a duplicate copy to a second path. Cancelling that
panel instead left the tab permanently detached: title "Untitled", and every later activation reset
`backingDocument.fileURL` to nil, so macOS autosave had no target for the session. The coordinator
now takes a `didSaveTab` closure wired to `EditorTabStore.updateFileURL(_:forTabID:)` and records the
URL before advancing. It affects every tab in the queue except the last, so it needs ≥2 dirty tabs
with the untitled one not last.

## Native save/close serialization (runtime QA, 2026-09-04)

Do not start a save from inside `WindowCloseController.windowShouldClose`, or close a window
from inside an `NSDocument` save delegate callback. Both paths deadlocked the real app on
macOS 26.6.2: main-thread samples stopped in `_NSDocumentSerializationSemaphore` while the
same thread still owned AppKit's can-close/save activity. Save All must return `false` from
the close attempt before starting its queue on the next main-queue turn. Each successful save
must likewise unwind before activating/saving the next tab or closing the window. Keep the
synchronous saved-URL write-back **before** advancing the queue.

`SaveAndCloseCoordinator` delegates successful closure to the container's `performCloseTab`
on that later turn. It must not remove the last tab itself or call `NSWindow.performClose`
directly: the existing DocumentGroup scene-dismissal path owns that operation. Capture the
alert's owning window before dismissing the alert. Cancelled saves end the coordinator without
retargeting or closing the tab. Hosted callback-order tests and real Save/Save All panel runs
cover these boundaries; no OS-specific visual policy changed.

## macOS 14 inspector titlebar separator

Sonoma's native SwiftUI inspector draws its leading separator through the window toolbar. The
toolbar search field is translucent, so the separator is visible behind the field. While the
Reading inspector is presented on macOS 14, `lineformToolbarBackground` paints the exact active
page color in the toolbar region, making the separator end at the content edge. The workaround is
strictly scoped to macOS 14 and to the open-inspector state: macOS 15+ keeps the established hidden,
transparent toolbar background, and closing the inspector on Sonoma restores it too. Do not widen
the workaround to later systems without a new visual regression.
