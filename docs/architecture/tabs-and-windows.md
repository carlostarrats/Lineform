# Tabs & window chrome

Multi-document tabs, the window/nav chrome rules they interact with, and background-tab data safety.

Extracted from `CLAUDE.md` so the always-loaded file stays scannable. Content is verbatim —
these are the same load-bearing notes, not a summary. Read this file before changing anything
in this area.

- **Multi-document tabs**: each window supports multiple open documents in a tab bar (appears automatically when 2+ tabs are open). Tabs are rectangular, flat, theme-aware, with close buttons and dirty indicators. Each tab maintains independent display mode (Write/Read/Preview). Keyboard shortcuts: **⌘T** (new tab), **⌘⇧W** (close tab), **⌘]** (next tab), **⌘[** (previous tab). Closing a dirty tab prompts to save (Save / Don't Save / Cancel). Native macOS window tabbing is disabled (`NSWindow.allowsAutomaticWindowTabbing = false`) to avoid duplicate tab bars. Tab state is managed by `EditorTabStore` (in `Lineform/Editor/EditorTabStore.swift`), with the UI in `TabBarView` (`Lineform/Editor/TabBarView.swift`). Sidebar file clicks open in a new tab or switch to an existing tab if the file is already open. Closing a window with non-active dirty tabs is blocked by a confirmation sheet so tabs are not silently discarded (`WindowCloseController` in `Lineform/Editor/WindowCloseController.swift`). Closing a **background** (non-selected) tab must NOT re-run `activateSelectedTab` (`EditorContainerView.performCloseTab` guards on `wasSelected`): the selection is unchanged, so re-activating would needlessly clear the still-active tab's live search/Find&Replace + caret and wipe its undo stack. **Tab bar placement (load-bearing, 2026-07-18):** the tab bar lives INSIDE `editorShell`, in the VStack the reading inspector attaches to — so the Reading drawer presents as a full-height trailing column rising under the toolbar/search (exactly like the no-tab case) and the tab strip ends at the drawer's edge. When the tab bar sat ABOVE the inspector's anchor, the drawer was pushed below the strip and drew a floating rounded-corner outline while the toolbar's inspector section tinted a hard-edged patch behind the search aligned with nothing. Do not move the tab bar back above `editorShell`. **Window chrome across the tab/inspector transition (four rules, all pixel-verified 2026-07-18):** (1) toggling the tab bar or inspector rebuilds the detail hierarchy and AppKit can reset the window's explicit appearance to light `.aqua`; `WindowChromeReader.ChromeView` re-asserts the themed appearance on **every** `viewDidChangeEffectiveAppearance` (idempotent via the drift guard). **The sidebar column collapse/expand (`isShowingOutline`/`columnVisibility`) is a THIRD rebuild source with the same reset.** Symptom: the native sidebar-toggle glyph — the one appearance-derived control in the nav band — paints black on the dark toolbar and STICKS, while every explicitly-colored SwiftUI control stays correct (the band itself still looks themed because it is painted by `window.backgroundColor`, which the reset does not touch — that asymmetry is what makes only the glyph go wrong). **Root cause, diagnosed 2026-07-25 round 2: `viewDidChangeEffectiveAppearance` can NEVER fire for this drift.** `EditorWindowChrome.apply` pins `window.contentView.appearance`, and `ChromeView` is a descendant of the content view, so it inherits that PINNED appearance; resetting `window.appearance` alone leaves ChromeView's `effectiveAppearance` unchanged and the self-heal is structurally unreachable. The titlebar does not inherit the content-view pin — it follows `window.appearance` — hence the black glyph. The first fix (a next-tick + ~0.35s re-assert pair chasing the slide animation) only narrowed the window and still lost to a reset landing after the last timer. **`ChromeView` now observes `window.appearance` directly (KVO)** and re-applies on drift — deterministic, timing-free, and independent of where the reset comes from. It cannot loop: the drift guard makes its own write a no-op on re-entry. Do NOT reintroduce timer-based re-asserts for the appearance; `ReassertWindowChromeOnHierarchyRebuild` now covers only the parts of `apply` that nothing observes (the window `backgroundColor`). Guarded by `testWindowChromeReaderHealsWindowAppearanceDriftWithoutAnEffectiveAppearanceChange`, which resets `window.appearance` and asserts the heal WITHOUT invoking any callback by hand (the older drift test invoked `viewDidChangeEffectiveAppearance` manually, which is exactly why it stayed green through the bug). (2) `WindowChromeReader.dismantleNSView` must NOT clear the window appearance — SwiftUI dismantles/recreates the view during those same rebuilds with no guaranteed ordering vs. the replacement's apply, and the clear is what flashed the nav or left it stuck light (black sidebar-toggle glyph on Quiet). (3) The nav band with tabs is themed by the WINDOW's `backgroundColor`, set to the theme page color in `EditorWindowChrome.apply`: without tabs AppKit extends the detail's root scroll view under the titlebar (the toolbar samples the page), but the tab strip as topmost view stops that extension and NO SwiftUI background — plain or `.ignoresSafeArea(.top)` — reaches the titlebar region from inside the inspector container (both tried; Paper's cream nav went neutral). (4) `TabBarView`'s bar fill uses `ignoresSafeAreaEdges: []` so the strip's grey never bleeds into the toolbar's backdrop region. (5) The toolbar MATERIAL is hidden (`.toolbarBackground(Visibility.hidden, for: .windowToolbar)` — spelled with explicit `Visibility`, the bare `.hidden` is ambiguous against ShapeStyle and times out type-checking) so the band shows the page-colored window backdrop directly: with the material, the band could never equal the page color on dark themes (it rendered visibly darker) and it washed Paper's cream toward neutral. Net effect, pixel-verified: the nav band is byte-identical with and without tabs in BOTH light and dark themes, and reads as the same surface as the page. **Known cosmetic limitation (investigated 2026-07-25, decision: ship as-is, do NOT re-investigate blindly):** on a theme switch (e.g. Quiet ↔ Original), the native toolbar chrome — the Aa (Reading Experience) button's native shell and the `.searchable` NSSearchField bezel — visibly CROSS-FADES to the new theme over a fraction of a second, while every custom SwiftUI control (mode segmented control, inspector, sidebar) flips instantly in the same transaction. The fade is intrinsic to the native bezel/material drawing; three independent attempts all produced zero change: (1) applying `window.appearance` inside a zero-duration `NSAnimationContext` with `allowsImplicitAnimation = false`, (2) pinning `appearance` directly on every `window.toolbar.items[].view` in the same pass as the window apply, (3) recursively stripping implicit layer transitions (`contents`/`backgroundColor`/`opacity` → `NSNull()`) on all toolbar item views. Conclusion: the cross-fade is composited inside the native shell (likely WindowServer material re-sample), outside app reach. **Fix options, if it ever becomes worth it:** (a) replace the control's shell with a custom capsule keyed on `usesDarkChrome`, the `EditorModeSegmentedControl` pattern — a working `EditorToolbarPillButtonStyle` for the Aa button was built and verified instant on 2026-07-25, then reverted by product decision (the custom look wasn't preferred over the fade; it was never committed — recipe: a `ButtonStyle` drawing a `Capsule` fill at white 0.10/black 0.06 rest, 0.16/0.10 hover, 0.22/0.14 pressed, 0.5pt hairline stroke, `padding(.horizontal, 9).padding(.vertical, 5)`, wired via `.buttonStyle(...)` in `EditorContainerView.toolbarControl(for:)`); (b) for the search field, replacing `.searchable` with a fully custom SwiftUI `TextField` capsule is the only guaranteed fix (wrapping the native `NSSearchField` would NOT fix it — the fade is in the bezel itself), and it means rebuilding the scope bar (This File/All Files), ⌘F/`searchFocused` binding, Esc/cancel behavior, and narrow-window overflow — a deliberately NOT-taken trade given the search UX's regression surface (see `docs/architecture/search.md`). **Known limitation (intentional):** tabs share the window's single undo manager, so switching tabs clears undo history (`activateSelectedTab` calls `undoManager.removeAllActions()`); per-tab undo stacks are deliberately out of scope (see `docs/superpowers/specs/2026-07-18-review-followups-design.md`). **Tab close is pointer-hover-only by design (no × at rest); VoiceOver/Switch Control users reach it via a per-tab "Close tab" accessibility action** (`TabBarView`, gated on `tabCount > 1`).
